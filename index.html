Проблема

У платформы был потолок по монетизации: комиссия с оборота даёт тонкую маржу. Нужен был независимый источник net revenue, масштабируемый вместе с клиентами.

Discovery через JTBD

Провёл 5 глубинных интервью с топ-производителями и дистрибьюторами (Mars, Mondelez, Heinz, Далимо, Проект Инвест). Цель не "что вы хотите от платформы", а какая боль блокирует рост в B2B e-com.

Инсайт: во всех 5 интервью независимо прозвучала одна и та же боль: невозможность прогнозировать и управлять спросом со стороны торговых точек.
Решение. Механика планов закупок

Производитель в своём кабинете ставит индивидуальный план для каждой ТТ (в рублях или штуках) плюс вознаграждение за выполнение (кэшбек, подарок, скидка). ТТ видит план, выполняет, получает бонус. Платформа берёт комиссию только с фактического оборота по выполненным планам.

Что пошло не так, и что я из этого вынес
Провал: сначала дали возможность ставить планы по блокам SKU ("минимум 3 из блока А плюс 5 из блока Б"). Логично, но adoption упал ниже 20%. Пользователи ТТ не справлялись со сложностью. Механика приостановлена.

Урок: мощность инструмента не равна его полезности, если пользователь не может удержать логику в голове. В следующих итерациях сначала валидируем сценарий на пользователе, потом даём продакшн. Недоразобрался с пользовательской стороной, так как был сфокусирован на плательщике.

Что дальше
  • Редизайн UI для роста adoption с 75% до 85% и выше
  • Дашборды "добить план" для ТТ. Визуальный прогресс до вознаграждения
  • Рекомендательная механика для производителя. Какой план оптимален для каждой ТТ на основе исторических закупок

Проблема

Enterprise-поставщики с тысячами SKU не могли использовать self-service ЛК. Ручное управление ассортиментом невозможно. Интеграция через API растягивалась на недели-месяцы или вовсе ломалась. ~30% крупных лидов терялись именно на этом этапе.

Решение. Сегментирование по типу 1С плюс Pareto-подход

Измерил распределение 1С-систем среди крупных клиентов: 80% используют одну из трёх версий (УТ 11, УНФ, ERP). Через внешний подряд заказал разработку модулей под эти три. Классический Pareto-подход. Для остальных 20% индивидуальный подряд, если клиент достаточно крупный.

Почему build через подряд, а не in-house: 1С-разработка это узкая специальность, держать в штате под эпизодические проекты неэффективно. Build-vs-buy выбор в пользу контракта.

Что пошло не так
  • Несовместимость с patch-версиями 1С. Каждое обновление 1С ломало часть кейсов, приходилось дорабатывать. Сейчас перерабатываем архитектуру маппинга справочников.
  • Документация под не тот профиль пользователя. Ожидали, что клиент позовёт 1С-специалиста. Часть пыталась ставить бизнес-пользователями и застревала. Переписываем документацию в user-friendly формат с визуальным мастером.
Связь с Кейсом 3

Проблема

1С-модули закрыли боль enterprise-клиентов. Но вторая половина рынка, средние поставщики с сотнями SKU, требовали другого инструмента. Ручная работа через аккаунта создавала операционный потолок масштабирования, интеграция через API им избыточна.

Решение. Сознательный MVP-для-сегмента

Вместо "запустим сырой MVP на всех" выбрал обратный подход: полноценный experience для 60% поставщиков, которым подходит текущий функционал. Остальных 40% пока не пускаю в ЛК, они работают по старой схеме через аккаунтинг, пока не достроим функционал. Это сознательное решение: в B2B негативный первый опыт стоит слишком дорого.

Что пошло не так
Ошибка в профиле пользователя: делали онбординг под технического специалиста, а реально с ЛК работает бизнес-пользователь (менеджер отдела продаж без IT-бэкграунда). Первые поставщики застревали на настройке API-ключей.

Что поменяли:

  • Зарефакторили онбординг под бизнес-пользователя. Визуальный wizard, тех-детали ушли с первого экрана
  • Ввели ролевую модель внутри ЛК: бизнес-пользователю не нужна API-документация, тех-спецу не нужна аналитика поведения

Главный урок: в B2B-продукте "клиент" не равно "пользователь". Компания не пользуется продуктом, пользуется конкретный сотрудник с конкретным контекстом.

Монетизация на подходе
  • Self-service продвижение товаров. Поставщик сам покупает выделение в выдаче без участия аккаунта
  • Аукционная модель. В популярных категориях поставщики конкурируют за топ-позиции, цена формируется динамически
Почему не A/B
В B2B-маркетплейсе с неравномерным распределением ассортимента и конкуренции по территориям классические A/B дают слишком высокий шум относительно продуктового эффекта. Вместо A/B использую cohort-анализ по времени, качественные интервью и локальные пилоты на отдельных территориях. A/B это правильный инструмент под правильный контекст, не самоцель.
